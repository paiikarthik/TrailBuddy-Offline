## 1. Concise Project Description

**TrailBuddy Offline** is an open-source, privacy-first Progressive Web App designed to reverse digital screen addiction. It pairs open-weight language models (via Ollama or hosted inference) with an intelligent in-browser fallback engine to generate structured, sensory-rich outdoor itineraries, track screen-free time in nature, and record personal observations in a 100% private local journal—guaranteed to work even when deep in the wilderness without internet access.

---

## 2. Problem Statement & Why This Project Matters

Modern technology is largely engineered around engagement metrics, push notifications, and screen time maximization. The average adult spends over seven hours a day consuming digital feeds, leading to sensory fatigue, fractured attention spans, and detachment from the natural environment.

Most existing outdoor and hiking applications counterintuitively exacerbate this problem:
1. They require account registration, persistent cellular signal, and GPS tracking.
2. They feature social feeds, notifications, and gamified badges that encourage users to stare at their phone while on the trail.
3. They fail completely in connectivity dead zones where people most need quiet contemplation.

**Why TrailBuddy Matters:**  
TrailBuddy measures its ultimate success by having users **close the application** and step outside. By providing structured itineraries, mindful sensory prompts, an analog-style screen-free timer, and local data persistence without accounts, TrailBuddy makes unplugging accessible, welcoming, and safe.

---

## 3. Technical Explanation: How Open-Source AI Supports the Goal

Rather than relying on proprietary, closed-source cloud APIs that require subscriptions, leak user habits, and break without internet connectivity, TrailBuddy leverages open-weight artificial intelligence:

1. **Local Open-Weight Model Support (Ollama):**  
   TrailBuddy natively communicates with local Ollama instances running efficient open-weight models such as `mistral` (7B) or `llama3.2` (3B). This allows users with standard consumer hardware to generate infinite variations of creative, sensory outdoor activities completely offline on their own machines.
2. **Strict Guardrails & Structured Output:**  
   The application uses system-prompt constraints requiring raw JSON schemas with nine mandatory fields (itinerary steps, household gear, mindful task, screen-free tip, safety checklist, and reflection prompt). It strictly instructs the model **never** to fabricate current weather, trail closures, opening hours, or GPS coordinates.
3. **Resilient Two-Tier Fallback Hierarchy:**  
   - If the AI request times out (>8s) or the model service is offline, the Flask backend invokes a deterministic heuristic engine (`services/planner.py`).
   - If the user has zero network connectivity to the backend server (e.g. out on a remote trail), the PWA client invokes a bundled in-browser JavaScript engine (`static/js/offline.js`).
4. **Transparent Provenance:**  
   Every generated plan carries an explicit badge indicating whether it was synthesized by an open-weight AI model or generated by the local offline rule engine.

# Touch Grass with TrailBuddy Offline: Building a Privacy-First AI Outdoor Companion

As developers, we are intimately familiar with screen fatigue. Between code reviews, pull requests, and endless browser tabs, modern life can easily become an unbroken series of glowing rectangles.

For **Hacktoberfest 2026 Week 1 ("Touch Grass")**, our team asked a contrarian question:

> **Can we build a piece of software whose primary goal is getting people to close the application and step outside?**

Meet **TrailBuddy Offline** — an open-source, privacy-first Progressive Web App that helps users discover personalized outdoor activities, practice sensory nature mindfulness, and log observations without ever leaking private data or requiring an active internet connection.

---

## Why "Offline-First" Matters for Outdoor Apps

Most outdoor planning apps suffer from a fundamental contradiction: they require cloud connectivity in places where nature is at its best — deep in forests, along coastal bluffs, and on mountain ridges.

When designing TrailBuddy, we established three non-negotiable architectural constraints:
1. **Zero Mandatory Accounts:** No sign-up walls, OAuth flows, or telemetry tracking.
2. **PWA Offline Resilience:** After the first visit, the entire application shell, curated datasets, and planner must work in airplane mode.
3. **Open-Weight AI with Deterministic Fallback:** Use open-weight models (via Ollama or hosted inference) for creative itineraries, but ensure a 100% reliable rule-based engine is always available as a fallback.

---

## The Resilient Architecture

TrailBuddy operates on a multi-tiered architecture:

```
[User Browser PWA]
       ├── Service Worker (Cache-First Shell & Assets)
       ├── Local Storage (Nature Journal & Screen-Free Timer)
       └── Client-Side Rule Engine (Zero-Network In-Browser Fallback)
             │
             ▼
[Flask Backend Server]
       ├── Security Headers (CSP, Frame-Options, nosniff)
       ├── Strict Schema & Input Validation
       ├── AI Planner Service (Requests with 8s Timeout)
       │     ├── Local Ollama (`mistral` / `llama3.2`)
       │     └── Hosted Open-Weight Endpoint (vLLM / TGI)
       └── Server-Side Rule Engine (`planner.py`)
```

### 1. The PWA Service Worker
We configured `service-worker.js` with specialized caching strategies:
- **Cache-First** for static assets, CSS, icons, and client scripts.
- **Network-First** for page navigations, gracefully falling back to a dedicated `/offline.html` page.
- **Network-Only** for `/api/plan`: we explicitly do not cache stale AI plans. If a network call fails, client-side JavaScript catches the exception and immediately invokes the bundled in-browser rule engine.

### 2. Guardrailed AI Planning
When calling an open-weight model, prompt injection and hallucination are serious concerns. We enforce strict guardrails:
- The system prompt forbids inventing current weather forecasts, trail closures, opening hours, or fictitious GPS coordinates.
- Responses must conform strictly to a validated 9-field JSON schema.
- If Ollama is unreachable, times out, or produces malformed JSON, TrailBuddy automatically serves the rule-based plan with a clear indicator tag: `🌿 Generated via Offline Engine`.

---

## Lessons Learned

1. **Software Can Measure Success by Absence:** Designing an app where the primary interactive feature is a stopwatch tracking time spent *not* using the screen changed our UX philosophy.
2. **Local Storage is Plenty for Personal Journals:** Users don't need cloud databases for personal reflection notes. Browser `localStorage` with JSON import/export provides ironclad privacy and zero server maintenance costs.
3. **Open-Weight AI is Production Ready:** Small open-weight models like Llama 3.2 (3B) and Mistral (7B) running locally via Ollama are more than capable of structured sensory creative planning.
